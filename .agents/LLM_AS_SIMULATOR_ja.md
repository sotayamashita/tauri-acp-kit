# LLM はシミュレーターである：フレーミングがエージェント設計に与える影響

## 中核テーゼ

> "LLM をエンティティとしてではなく、シミュレーターとして考えよ。"
> — Andrej Karpathy

LLM にはアイデンティティも、意見も、専門性もない。次トークン予測器である。コンテキストが与えられると、次のトークンの確率分布を出力する。「判断」「専門知識」「視点」のように見えるものはすべて、入力コンテキストによってその分布がどう形成されたかの結果に過ぎない。

`"You are a senior engineer"` と書いても、LLM はシニアエンジニアにはならない。ファインチューニングデータの統計から暗示されるパーソナリティ埋め込みベクトルを採用し、それをシミュレートする。シミュレーションは有用な出力を生むかもしれないが、メカニズムは非人格的だ — コンテキストに条件付けされたパターン補完であり、それ以上ではない。

この区別は哲学的なものではない。エージェント設計において測定可能な帰結をもたらす。

## エンティティフレーミングが失敗する理由

エンティティフレーミングは LLM を何か「である」かのように扱う：「あなたは専門家です」「あなたはセキュリティスペシャリストです」「あなたはシニアコードレビュアーです」。研究は一貫して、このアプローチが非効果的または有害であることを示している。

### ペルソナ名はパフォーマンスを改善しない

- **Zheng et al. (EMNLP 2024 Findings)**: 4つの LLM ファミリーで 162 のペルソナを 2,410 の事実質問でテスト。ペルソナプロンプトはペルソナなしベースラインに対して一貫した改善を示さなかった。平均効果はわずかに**マイナス**。
- **Mollick et al. (Wharton GAIL, 2025)**: 6 モデルを GPQA と MMLU-Pro で評価。ドメイン一致のペルソナ（例：物理学の質問に「物理学者」）を含む専門家ペルソナは、統計的に信頼できる改善を示さなかった。統計的に有意な**マイナス**効果が 9 件観察された。
- **Pornprasit & Tantithamthavorn (IST, 2024)**: コードレビュー自動化で、ペルソナの追加（「熟練したソフトウェア開発者のふりをしてください」）により Exact Match が 1〜54% 低下。ペルソナなしのプロンプトにファインチューニングまたは few-shot 例を加えた方が一貫して高いパフォーマンスを示した。
- **CoReEval (2025)**: コード可読性評価で Junior vs. Senior ペルソナを直接比較。平均スコア：3.75 vs. 3.77。有意差なし。

### メカニズムの説明

Kirsanov et al. (NAACL 2025 Findings, "The Geometry of Prompting") は、異なるプロンプトタイプが内部表現にどう影響するかを分析した：

| プロンプトタイプ        | 影響するレイヤー                       | 分布シフトの深さ                          |
| ----------------------- | -------------------------------------- | ----------------------------------------- |
| ペルソナ / 指示テキスト | 主に最終レイヤー（出力パッケージング） | 浅い — リードアウトアラインメントのみ変化 |
| Few-shot 例 (ICL)       | 中間レイヤーが根本的に再構造化         | 深い — 表現幾何学そのものが変化           |

ペルソナ名は最も浅いレベルの影響しか及ぼさない。モデルが入力を処理する方法を再構造化せずに、出力パッケージングを微調整するだけである。これが弱く信頼性の低い効果しか生まない理由だ。

### パーソナリティ埋め込みベクトルの問題

「you」で強制された場合、LLM はファインチューニング統計から導出された汎用パーソナリティベクトルを採用する。このベクトルは：

- 特定のタスクに合わせて調整されていない
- 訓練データにおけるペルソナラベルに関連する無関係な特性を混入させる
- ノイズを導入しうる：Hu et al. (2024) は、無関係なペルソナ詳細（名前、好み）が最大 30 パーセントポイントのパフォーマンス低下を引き起こすことを発見
- タスク関連情報とアテンション重みを奪い合う

## シミュレーターフレーミングが機能する理由

シミュレーターフレーミングは LLM に何かで「ある」ことを求めない。「このコンテキストが与えられたとき、このプロセスは何を生成するか？」と問う。

### 実際に分布をシフトさせるもの

研究は 3 つの効果的なメカニズムを特定している（効果の深さ順）：

**1. Few-shot 例（最も深い効果）**

Kirsanov et al. (2025) は、デモンストレーションが中間レイヤーの表現を再構造化することを示した — 実際の「推論」パターンが計算されるレイヤーである。Agarwal et al. (NeurIPS 2024 Spotlight) は、十分な例があれば ICL が事前学習バイアスを完全にオーバーライドできることを実証した。

**2. 明示的な基準仕様（中程度の効果）**

IFScale (Jaroslawicz et al., 2025) は、指示が出力分布を効果的に制約することを確認したが、Claude ファミリーモデルでは指示数に応じて遵守が線形に低下する。重要な発見：負荷がかかると、モデルは後の指示を誤って適用するのではなく省略する。初頭性バイアスは普遍的である。

**3. 知識コンテキスト注入（中程度の効果）**

Ericsson (2025) は、リポジトリ構造や設計文書をコードレビュープロンプトに注入することが、ペルソナ割り当てよりもはるかに効果的であることを発見した。注入された知識は条件付き分布を直接変化させる：`P(output | criteria + domain_knowledge)` は `P(output | persona_name)` とは根本的に異なる分布である。

### シミュレーターフレーミングは 3 つすべてを自然に活用する

```
エンティティ:  "あなたはドメインエキスパートです。このコードをレビューしてください。"
               → 汎用パーソナリティベクトルを活性化。浅く、ノイジー。

エグゼキューター: "名前がドメイン語彙に一致しているか評価せよ。"
               → 出力を制約。機能するが、LLM をエグゼキューターと仮定。

シミュレーター: "以下のドメイン用語集が与えられたとき: [用語集]
               そしてこのコード変更: [diff]、
               ドメインに焦点を当てたレビューはどのような命名の
               不整合を特定するか？"
               → 知識をシミュレーションコンテキストとして注入。
               → 基準をシミュレーションの焦点として指定。
               → 出力は自然にシミュレーション結果の形をとる。
```

シミュレーターフレーミングは：

- **アイデンティティを宣言しない** — 「あなたは〜です」がない
- **実行を命令しない** — 「〜を評価せよ」がない
- **シミュレーションコンテキストを設定する** — 知識 + 基準 + スコープ
- **シミュレーションが何を生成するかを問う** — コンプライアンスではなく、発見事項

## 3 つのフレーミングの比較

| 側面                     | エンティティ（ペルソナ）              | エグゼキューター（ジョブ） | シミュレーター                       |
| ------------------------ | ------------------------------------- | -------------------------- | ------------------------------------ |
| 中核プロンプト           | "あなたは X です"                     | "X を実行せよ"             | "X は何を発見するか？"               |
| 分布シフトメカニズム     | パーソナリティベクトル（浅い）        | 出力制約（中程度）         | コンテキスト条件付け（深い）         |
| 知識注入                 | 暗黙的（「あなたの専門知識」）        | 明示的（入力パラメータ）   | 自然（シミュレーションコンテキスト） |
| 出力フレーミング         | 「私の評価は...」                     | 「結果: ...」              | 「レビューは以下を発見する...」      |
| 実証的裏付け             | マイナス (Zheng, Mollick, Pornprasit) | プラス (IFScale, Ericsson) | 最も強い (Kirsanov, Agarwal)         |
| LLM の本質に対して誠実か | いいえ — アイデンティティの存在を偽装 | 部分的 — 関数として扱う    | はい — シミュレーターとして扱う      |

## マルチエージェント設計への示唆

単一の LLM がシミュレーターであるならば、マルチエージェントシステムは**非干渉シミュレーションの集合**である。

### 複数シミュレーションを使うべきとき

2 つのシミュレーションを単一シミュレーター内で同時に実行すると干渉が生じる場合、別エージェントで実行すべきである。4 つのテストがこれを判定する：

**テスト 0 — 生成-検証の独立性**

> 出力を生成したのと同じシミュレーションが、その出力を信頼性をもって検証できるか？

できない。Huang et al. (ICLR 2024) は、内在的自己修正が推論パフォーマンスを低下させることを証明した。Tyen et al. (ACL 2024) は、LLM が推論エラーを「発見」することはできないが、エラー位置が与えられれば「修正」できることを示した。Li et al. (2025) はそのギャップを定量化した：Claude のエラー検出率は 10.1% だが、修正率は 29.1%。

エラーを生成したのと同じ条件付き分布では、そのエラーを検出できない。検証には異なるシミュレーションコンテキスト — 異なるエージェント — が必要である。

**テスト 1 — コンテキスト干渉**

> シミュレーション A に必要な知識が、同一コンテキストに配置されたとき、シミュレーション B の効果を希釈するか？

知識希釈 (NeurIPS 2025 Workshop) は、コンテキスト的に関連するがドメイン的に無関係な情報にさらされると、ドメイン固有のパフォーマンスが最大 47% 低下することを実証した。2 つのシミュレーションが異なる知識ベース（例：ドメイン用語集 vs. API コントラクト）を必要とする場合、1 つのコンテキストに混合すると両方が希釈されるリスクがある。

**テスト 2 — 分布互換性**

> シミュレーションの評価基準は、出力分布を互換的な方向にシフトさせるか？

Kirsanov et al. (2025) は、同じ入力分布を共有するタスクは相乗的になりうるが、矛盾する分布シフトを必要とするタスクは干渉することを示した。例：「この名前はドメイン的に適切か？」と「この時間的順序はアーキテクチャ的に健全か？」は異なる語彙、異なる抽象レベル、異なる評価フレームワークを必要とする — これらは分布非互換である。

**テスト 3 — アテンション予算**

> 統合された基準数が遵守閾値を超えるか？

IFScale (2025) は、Claude ファミリーモデルが指示数に応じて線形に遵守が低下することを確立した。アテンションシンク研究 (ICLR 2024, 2025) は、これが softmax 正規化の構造的制約であり、プロンプトエンジニアリングの問題ではないことを示した。実用上の限界：エージェントあたり同時評価基準 7 以下。

### エージェント定義テンプレート（シミュレーターフレーミング）

```
Simulation:  シミュレートする評価プロセス
Context:     シミュレーションを条件付ける知識
Focus:       具体的な基準（7 以下） — シミュレーションのレンズ
Input:       評価対象
Output:      構造化されたシミュレーション結果
Depends:     入力として必要な他のシミュレーションの結果
```

例：

```
Simulation:  ドメイン命名一貫性レビュー
Context:     ドメイン用語集、概念境界定義
Focus:
  1. 各名前は用語集の用語と一致しているか？
  2. 各名前の抽象レベルはそのモジュールに適切か？
  3. 概念境界は守られているか（絡み合いがないか）？
Input:       変更ファイルの git diff
Output:      Finding[] { location, evidence, judgment }
Depends:     なし（独立シミュレーション）
```

### メタシミュレーターとしてのリーダー

Karpathy の提案 — 「xyz を探求するのに適した人々のグループは何か？」 — はチームリーダーの役割に対応する：

1. **変更を分析する** — これはどのような種類の変更か？
2. **有用なシミュレーションを決定する** — 「この変更にとって価値のある評価の視点は何か？」
3. **シミュレーションエージェントを起動する** — スコープが関連するシミュレーションのみを活性化する（適応的活性化）
4. **統合シミュレーションを実行する** — 「これらのシミュレーション結果を踏まえて、矛盾や偽陽性は何か？統合された評価は何か？」

リーダーはメタシミュレーションを実行する：どのシミュレーションを実行するかを決定するプロセスをシミュレートし、その後それらの出力を検証・統合する。

## 確率論との接続

上記すべては単一の原則に帰結する：**LLM エージェントは設定された条件付き確率分布である**。

```
P(output | simulation_context, criteria, knowledge, input)
```

- **ペルソナフレーミング** は `simulation_context` を曖昧なパーソナリティベクトルに設定する — 低情報量、高ノイズ
- **ジョブフレーミング** は `criteria` を明示的に制約する — 中程度の情報量、中程度のノイズ
- **シミュレーターフレーミング** はすべての条件付け変数の情報量を最大化する — 知識は直接注入され、基準は具体的で、出力は個人的判断ではなくシミュレーション結果としてフレーミングされる

マルチエージェント設計は、条件付け変数の空間を非干渉部分集合に分割する問題である。各部分集合が 1 つのエージェントのシミュレーションコンテキストとなる。
